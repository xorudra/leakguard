## WHAT WAS IMPLEMENTED
- **Budget engine** (Phase 158, `scanning/budgets.py`):
  per-user daily full-scan budget — 50 hand-started scan
  jobs per signed-in user per UTC day, operator-set in the
  Phase 66/124 pattern (recorded arithmetic: the existing
  `user_scans` rate limit caps bursts at 10/hour, so the
  daily budget binds only sustained all-day automation —
  the slow runaway hourly windows cannot see; a fresh user
  is nowhere near it). Enforced inside the create_job
  insert transaction; refusal is the house typed shape —
  `ApiError(429, "scan_budget_exhausted", …)` with a plain
  message naming the limit, the midnight-UTC reset, and the
  monitoring exemption — and a refused job is never queued
  (test-asserted: the row does not exist). Idempotent
  retries return the existing job and are never refused;
  consent/identifier checks still run first, exactly as
  before. `budgets_snapshot()` reads every budget live
  from its enforcing constant (discovery 6 from the
  orchestrator, probe 40.0 s from the remediation engine,
  provider budgets from providers/usage.py, route limits
  from core/ratelimit.py), each with its source, into the
  admin metrics `budgets` block — the registry cannot
  drift from enforcement.
- **Scheduled-lane decision** (Phase 158): monitoring
  scans do NOT count against and are NEVER refused by the
  manual budget. The scheduler inserts jobs directly under
  `monitor-…` idempotency keys (authorized by the
  'monitoring' consent, already bounded to one per cadence
  period), so enforcement in create_job structurally never
  sees them, and the count query excludes the `monitor-`
  prefix. A hand-scan spree cannot starve the monitoring
  the product exists to do.
- **Data-quality stage** (Phase 160,
  `scanning/data_quality.py` + migration
  `0015_data_quality.sql`): a guarded ~daily pass over
  stored findings, riding the scheduler tick after the
  alerts step behind the same flag + try/except guard.
  Duplicates are detected on the job-scoped key (job_id,
  identifier_id, provider, source_name, source_url,
  evidence_ref; rows past the first by discovered_at, id);
  malformed rows are caught by a pure per-row contract
  checker for what DB CHECKs cannot see — details not a
  JSON object, pwned_count not a non-negative int (bool
  excluded), dns summary not {rtype: [strings]},
  exposed_fields null/empty/non-string entries, blank
  source identity, bad source_url shape, off-enum
  confidence/reliability (defence-in-depth). Migration
  0015 adds findings.dq_duplicate / dq_malformed flags
  (recomputed to current truth every run), a dq_runs
  ledger, and dq_issue_rollup (provider, day, kind,
  count) — the per-provider drift time-series. Results
  surface in the admin metrics `data_quality` section;
  when malformed rows stand after a run, exactly one
  PII-free audit row (data_quality.issues, counts only)
  is written; duplicates alone raise none.

## WHAT WAS DELIBERATELY NOT IMPLEMENTED
- Cross-job duplicate flagging: the same exposure identity
  across different jobs IS the monitoring design (the
  lifecycle writer's identity in monitoring/diff.py), not
  duplication. A test proves a cross-job repeat stays
  unflagged.
- Any read-path change for flagged rows: every findings
  reader was checked (public finding view, action center,
  scores, lifecycle writer) — none filters on the new
  flags, so flagged rows stay fully visible and counted
  exactly as before. The stage flags and reports; it never
  silently deletes or hides a user's findings.
- The org budget tier: the product has no organizations
  or teams. Households (migration 0007) are member labels
  inside one account, not budget principals — the
  docstring says so plainly instead of inventing a tier.
- Anonymous per-user budgets: anonymous traffic has no
  identity by design and stays governed by per-IP rate
  limits.
- Admin-UI grid rows for the new metrics blocks: the
  metrics JSON carries both `budgets` and `data_quality`
  sections (the P2-C/D pattern was API + UI; this cycle
  scoped surfacing to the metrics block). A UI row is a
  follow-up if the owner wants it.

## SECURITY CONTROLS
The budget gate runs inside the job-insert transaction
(no check-then-act window); refusals leak nothing beyond
the user's own count state. DQ audit rows are counts-only
scalars; the stage writes flags on findings but never
content. Metrics additions inherit the admin 404 gate.

## PRIVACY CONTROLS
DQ examines stored findings in place and records only
aggregate counts externally (rollup by provider/day/kind);
no finding content leaves the database. The per-user
budget counts a user's own jobs for that user's own
refusal decision — no cross-user surface.

## KNOWN LIMITATIONS
The 50/day figure is operator judgment sized against the
10/hour burst cap, not a measured demand curve; the first
real refusal will be visible in metrics and the message
tells the user exactly what happened. The DQ duplicate
key is deliberately narrow (job-scoped): a provider that
double-reports the same exposure under two URLs inside
one job is drift, caught by the malformed/drift rollups
only if it also breaks the contract — semantic near-dup
detection is out of scope and unclaimed.

## RISKS
budgets_snapshot() reaches the probe budget through a
deferred inspect-based read of the remediation engine's
constant; if that attribute is ever renamed, the snapshot
test fails loudly (by design) rather than the registry
drifting silently. The DQ pass scans all findings per
run; at today's scale (1,498 rows on staging) it is
trivial, and the ~daily self-gate bounds its cost as the
table grows.
