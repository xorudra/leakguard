## WHAT WAS IMPLEMENTED
- **Latency alert rule** (Phase 175,
  `monitoring/alerts.py::_scan_latency`): appended to the
  rule list after the existing five (their behavior
  unchanged), evaluated in the same scheduler-tail
  position, delivered through the same path (audit row +
  admin email via engineering_alert mode "always",
  dedupe `eng:scan_latency:<UTC date>`). Fires when the
  median completed-scan duration over the trailing 24 h
  ≥ 120 s across ≥ 10 completed jobs, computed with the
  exact query the admin metrics publish
  (percentile_cont(0.5) over finished_at − started_at,
  status='done') — one definition of scan duration
  everywhere. Threshold arithmetic is in the module
  docstring (see RESULTS).
- **Alert drill** (docs/drills/2026-10-08-latency-alert-drill.md):
  a tabletop-format walk of the rule firing end-to-end on
  seeded data in the test environment (recording fake
  email lane), honestly typed as such — no staging or
  production claim. Walks what the admin sees (email,
  audit row, metrics agreement), the ack reality (no ack
  button exists; the daily dedupe is the de-facto ack;
  the scheduler kill switch is the emergency mute), and
  four named gaps (G1–G4 below).
- **Monitoring summary** (docs/MONITORING.md, new): the
  single home answering "how is LeakGuard watched?" —
  UptimeRobot (external, 5-min, HEAD-safe) → error ledger
  (hash-only, hourly rollup, 30-day prune) → all six
  alert rules in one thresholds table → the latency
  definition → provider budgets (operator-set values
  named as such; Brevo's published 300/day distinguished)
  → per-deploy live-verification practice → honest limits
  including the in-process/sleep caveat.
- **Cleanup audit + decision** (Phase 178, recorded in
  docs/DOC_REVIEW.md as a dated section): four sweeps —
  repo-wide reference grep; server-graph grep over app.py
  + all 9 packages + agent.py (ZERO references to the
  three local-only files); AST import audit; dead-file
  sweep of all root scripts + tools/*.py. **Decision:
  KEEP all three as documented local-only surface** —
  local_agent.py (user-run device runner for
  Cloudflare-walled brokers), proxy_relay.py (CONNECT
  relay used by the probe and both tools/ live checks),
  browser_probe.py (local Playwright probe). Removal
  candidates: NONE — no file met the proof bar
  (unreferenced by code, tests, tools AND docs), so
  nothing was deleted. The three files' headers now
  state their local-only status + purpose in the file
  itself, and two architecture tests pin the invariant
  (app.py never imports the local-only scripts; the
  scripts stay local).

## RESULTS
The latency rule's arithmetic, stated plainly: healthy
scans complete in seconds (P2-B measurements; the worst
healthy figure ever recorded is ≈60 s for a whole
214-identity monitoring cycle's convergence), so a
120-second MEDIAN across at least 10 completed jobs in
24 h is ≥2× the worst healthy band — the typical job has
degraded. Below 10 jobs the rule cannot fire at all: a
quiet system's "median" is one job's weather (a cold
Neon wake, one huge profile), and alerting on it would
train the operator to ignore the channel.

## KNOWN LIMITATIONS
The nuance the Phase 178 audit surfaced, recorded
verbatim in spirit: browser_probe.py is NOT reachable
"only from the local agent" as the earlier shorthand
claimed — agent.py's subprocess spawn sits inside
probe_with_browser_fallback, which the anonymous
POST /api/agent/probe route also calls in deep mode. It
is bounded four ways (subprocess isolation + timeout;
the route's per-IP rate limit; the Phase 166 allowlist
enforced before Playwright imports; deployed-server
inertness — Playwright/Chromium ship only in
requirements-optional.txt, so on Render probe() returns
its honest "not installed" blocker, and
LEAKGUARD_NO_BROWSER=1 disables the spawn outright; the
remediation engine never touches it). The drill's four
gaps stand as recorded: G1 detection latency up to one
hourly scheduler tick; G2 a spun-down instance evaluates
nothing (UptimeRobot is the always-on layer by design);
G3 stall ≠ slowness (queue_buildup/worker_failures own
stalls); G4 median-only, no p95 rule yet.

## RISKS

is recorded with its arithmetic so a future operator can
