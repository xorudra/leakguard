## WHAT WAS AUDITED
The cost surface as the audit left it: all providers free by
owner rule with `cost_model` metadata, fixed discovery/probe
budgets, and rate limits — but nothing counted how much of
each provider's free capacity the product actually consumes,
nothing enforced a per-provider budget, and nothing would
alert before a free tier ran dry. Also audited first:
`tests/test_architecture.py` — providers/ is a leaf package
(no project imports), which dictates where a persistent
ledger may live; `providers/base.py` HealthTracker (the one
choke point every provider call flows through); and the
notification lane, to establish whether Brevo belongs in the
provider budgets (it does not — see below).

## WHAT WAS IMPLEMENTED
- **Usage ledger** (Phase 124): migration
  `0014_provider_usage.sql` creates `provider_usage_daily`
  (provider, day, calls, successes, failures). Counting lives
  in `providers/usage.py` (in-memory tracker + budget config,
  stdlib-only, leaf-safe); persistence is INJECTED by
  `accounts/provider_usage.py` (upsert + read-back), installed
  once at startup from `app.py`. One logical call = one
  `HttpClient` outcome (retries collapse — the HealthTracker
  granularity). Flush is batched (every 25 pending, plus
  flush-before-read in metrics/alerts); a failed flush merges
  counts back (never lost, never doubled); the loader
  re-seeds today's counts after a restart. Refusals that
  never reached a provider (circuit-open, budget) are health
  events, not usage.
- **Budgets** (Phase 66): per-provider daily call budgets in
  `providers/usage.py` — XposedOrNot 5,000, HIBP Pwned
  Passwords 5,000, DuckDuckGo discovery 1,000 (politeness:
  a scraped public endpoint, already capped at 6 queries/job
  with a 1 s minimum interval), username platforms 20,000
  (13 probes per check), domain intel 10,000. Every value is
  documented in code as an OPERATOR-SET safety budget
  derived from call arithmetic — none of the keyless APIs
  publishes a numeric daily quota, and no published quota is
  claimed anywhere. A parity test asserts BUDGETS names
  exactly the live registry's providers.
- **Enforcement** (Phase 66): at 100% of a provider's daily
  budget the provider layer refuses further calls until the
  next UTC day with the existing typed shape
  (`ProviderResult` error_kind `budget_exhausted`), which
  the orchestrator already surfaces as a provider_error
  outcome + a degraded job — reduced coverage is reported,
  never silently swallowed. Enforcement is fail-open: any
  tracking failure lets the call proceed. Per-user tracking
  is counts-only (admin metrics `today` block: scan jobs /
  distinct users / max jobs per user, from scan_jobs'
  existing user_id).
- **Monitoring + spend alerting** (Phase 124): the admin
  metrics block gains a `providers` section (today's calls /
  successes / failures, budget, % used, exhausted flag per
  provider) rendered as compact rows in the admin UI; one
  new alert rule `provider_budget` fires at any provider
  reaching 100%, through the P2-C engineering_alert path —
  one email per day maximum (dedupe `eng:provider_budget:
  <date>`), the audit detail naming the exhausted providers.
  Monitoring tracks call volume against free budgets; spend
  is ₹0 and no money figure is fabricated anywhere.

## WHAT WAS DELIBERATELY NOT IMPLEMENTED
- Brevo in the provider budgets: the provider layer sends
  no email. Brevo's published 300/day cap binds the
  notification lane, already governed by the P2-B digest
  design (per-finding email is impossible by construction).
- Per-user budget ENFORCEMENT: per-IP rate limits (anonymous)
  and per-provider budgets (global) are the enforcement
  layers that exist honestly today; per-user quotas would
  change product behavior beyond the audited gap. Tracking
  is in place if the owner ever wants them.
- A retention prune for `provider_usage_daily`: ~5 rows/day
  and the history IS the Phase 124 cost record — stated in
  the migration header.
- Anonymous per-user tracking: anonymous traffic has no
  identity by design; the usage module docstring says so
  plainly instead of inventing one.

## SECURITY CONTROLS
Usage data is counts only — no request content, no user
identifiers in the ledger; per-user figures are aggregates
in the admin-gated metrics payload (counts-only per the
admin privacy contract). The budget gate fails open for
availability but can never be used to amplify traffic: it
only ever refuses.

## KNOWN LIMITATIONS
Budget values are operator judgment, not provider-published
limits (none exist in published form for these keyless
APIs); if a provider ever publishes a real quota, the
constant should be replaced with it. One-call granularity
collapses transport retries, matching HealthTracker — a
provider that retries internally still counts once. The
recorded import graph gains a function-level
monitoring→providers edge (alerts reads the tracker);
architecture tests pass and the edge follows monitoring's
deferred-import pattern.

## RISKS
A budget set below a future traffic spike would degrade
scans honestly (provider_error + degraded flag) rather than
fail them — visible in metrics and announced by the
provider_budget alert a day's-end early at the latest.
Fail-open tracking means a broken ledger degrades to
P2-C-era visibility (HealthTracker counts), never to an
outage.
