## WHAT WAS AUDITED
The four surface gaps as the audit left them: the admin
overview knew whether broker opt-out PAGES were reachable
but not whether brokers actually REMOVE people or which
removal workflows were failing; discovery (search-engine)
findings existed only buried inside scan results, with the
6-queries-per-job cap never formally reviewed; the shell
had zero aria-* attributes and no accessibility checks of
any kind; and the no-cache-for-API privacy design was a
convention responses were trusted to follow, not a
mechanism. Also audited: the findings construction for
discovery (both markers that distinguish a public-web
mention from every other finding kind), the response
choke point in app.py, and the service worker's fetch
handling.

## WHAT WAS IMPLEMENTED
- **Broker health dashboard** (Phase 125,
  `accounts/admin.py::_broker_health_block`): per broker
  with any removal activity — verification checks count +
  outcome distribution (still_listed / gone / unknown)
  + latest check, cases by status, attempts by result —
  added to the admin overview payload and rendered in the
  Admin card as a compact "Broker health" table next to
  the existing opt-out-page reachability. Tests assert the
  aggregates against seeded checks/cases/attempts.
- **Search exposure view** (Phase 40,
  `dashboard/search_exposure.py` + `GET /api/search-exposure`
  + an SPA section): returns only the caller's own
  discovery findings — the selection pins BOTH
  construction markers (the discovery provider AND
  details.match_kind = 'public_web_mention') so breach,
  platform-presence and domain findings can never leak
  into the view — grouped by saved detail, values masked
  by the vault, owner-scoped by construction. The view's
  copy states the honesty rule: a mention is a lead to
  review, never a confirmation.
- **Cap review** (Phase 40, second leg): KEEP
  DISCOVERY_BUDGET = 6. The cap is a politeness budget
  against a scraped, keyless endpoint whose tolerance is
  the scarce resource; six queries cover six non-email
  details per job; over-budget identifiers are reported
  'budget_exhausted' (never silently skipped) and
  re-checked next monitoring cycle; platform load is
  already governed by the P2-D daily DDG budget
  (1,000/day) and the Phase 158 per-user budget, so a
  higher per-job cap would only drain the shared budget
  faster. Full reasoning in the module docstring.
- **Accessibility** (Phase 96): audit + fixes —
  aria-labels on icon-only controls, a "Skip to the scan"
  skip link, polite aria-live regions on the status /
  notification / search-exposure surfaces (acStatus,
  rsStatus, notifList, searchExposureList), focus-visible
  styling. Visible copy and primary button labels
  unchanged. Checks at two levels:
  tests/test_accessibility.py (CI invariants over the
  shipped source) and tools/a11y_check.py (rendered-DOM
  assertions on the live site, Phase 97 idiom).
- **Caching policy pinned** (Phase 67): every API
  response — JSON success or error, and the privacy
  export download — now carries `Cache-Control: no-store`
  set at the single response choke point in app.py; the
  shell/static files stay header-free and are stored only
  by the service worker's explicit shell list, which
  never intercepts /api/*. tests/test_api.py asserts the
  headers across representative API responses.

## WHAT WAS DELIBERATELY NOT IMPLEMENTED
- Raising the discovery cap (see the review above —
  changing it without measured under-coverage evidence
  would trade a shared-resource risk for nothing).
- Any server-side response caching (the phase's ask is
  to PIN the no-cache design, not reverse it).
- An accessibility redesign: visible copy and primary
  labels are load-bearing for users and for the live
  smoke flows; the pass is attributes + structure +
  focus visibility.
- A discovery "confirmation" concept: the data cannot
  support one, and inventing it would break the view's
  honesty rule.

## SECURITY CONTROLS
The search-exposure endpoint is owner-scoped by
construction (the session's user id scopes every query;
another user's findings are unreachable) and returns
masked values only. The no-store header is set at the
choke point, so future routes inherit the privacy
policy instead of remembering it. Admin surfaces remain
404-invisible to non-admins.

## PRIVACY CONTROLS
Discovery findings are shown only to their owner, only
masked, and labeled as unconfirmed mentions. no-store
keeps account data out of every downstream cache. The
broker health block is counts/outcomes only — no user
data in the admin surface, as ever.

## DEPLOYMENT STATUS
Production and staging both on `192ce5e`, live-verified.

## KNOWN LIMITATIONS
The search-exposure view is only as full as the
discovery data: email-only profiles legitimately show
the empty state (discovery targets phone/name/address/
username details), and weak-confidence mentions need a
human's judgment — the view says so rather than scoring
them. The a11y checks assert DOM-level invariants
(labels, landmarks, live regions, heading order); they
are not a full WCAG audit and do not claim to be. The
service worker's shell update lag (one load cycle on
returning browsers) is inherent to the shell-caching
design pinned in Phase 67.

## RISKS
The per-broker health block reads three more tables per
admin overview load; it runs only for admins on the
overview path (the aggregates-only surface), never on
user paths. The choke-point header touches every API
response by design — the suite's API tests plus both
live E2E smokes cover the blast radius.
