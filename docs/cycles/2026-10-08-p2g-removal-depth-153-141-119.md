## WHAT WAS AUDITED
The removal engine's decision-making as the audit left it:
correct but embodied — probe transitions, consent
re-checks, and channel derivation were interleaved with IO
inside `remediation/engine.py`, unversioned and not
unit-testable as pure decisions. Case states differed from
the spec's vocabulary with no published mapping. Jobs and
cases that exhausted their attempts reached a persisted
dead/failed state with no way back — no replay tooling
existed. Also audited: the audit writer's actor model, the
house admin surface (to place replay where it belongs),
retry_case's own refusal vocabulary (respected, not
duplicated), and the one-live-case partial unique index.

## WHAT WAS IMPLEMENTED
- **Policy engine** (Phase 153, `remediation/policy.py`,
  new): stdlib-only, zero project imports, pure data in /
  data out. `POLICY_VERSION = 1`; the full decision table
  as `decide_*` functions returning decision dicts
  {status, reason, attempt, mark_submitted} —
  unknown-broker, consent, email, manual, probe (with
  missing_field), probe transitions, submit — plus
  `derive_channel` (registry_seed delegates) and
  `probe_attempt_word`. `engine.process_case` now does IO
  only, applying decisions through the unchanged
  `_transition` choke point via a thin `_apply_decision`
  adapter; `interpret_probe` remains as a delegating seam
  (it passes agent.PROFILE_FIELDS in, so the policy never
  imports `agent`).
- **State mapping** (Phase 141): `policy.SPEC_STATE_NAMES`
  — a formal mapping total over the 8 stored states
  (queued→QUEUED, running→IN_PROGRESS, submitted→SUBMITTED,
  needs_human→AWAITING_USER, blocked→REJECTED,
  verified_removed→VERIFIED_REMOVED, reappeared→REAPPEARED,
  failed→FAILED); `SPEC_STATES_WITHOUT_INTERNAL_STATE`
  declares AUTHORIZED and NOT_STARTED as expressed by
  consent-gated case creation — no states invented.
  `service.public_case` gains the additive `spec_status`
  field, flowing to case list, case detail, human queue,
  retry and verify payloads (all share that serializer);
  no field renamed. `docs/REMOVAL_STATES.md` publishes the
  mapping and the consent-gated-creation note.
- **Dead-letter replay** (Phase 119,
  `accounts/admin.py::replay_dead_letter` +
  `POST /api/admin/replay`): returns one dead scan job or
  failed case to the queue. Jobs: attempt counter resets
  to 0 (a fresh 3-attempt budget) with error/timing fields
  cleared. Cases: the append-only attempts history is left
  exactly as it stands; the worker appends after it. Every
  replay re-checks the owner's CURRENT consent per lane
  (cases → automated_remediation; monitor- jobs →
  monitoring; hand-started jobs → scanning) and writes an
  `admin.dead_letter_replayed` audit row (actor = the
  admin, PII-free, carrying the preserved death record).
  The response carries only {kind, id, status} — the
  admin module's aggregates-only privacy contract holds
  even for its one write operation.

## WHAT WAS DELIBERATELY NOT IMPLEMENTED
- State RENAMING (Phase 141's other route): migrating
  stored rows, the 0005 CHECK, notification copy, and
  client code to the spec's names buys zero user benefit
  at real risk; the phase text names the formal mapping
  as a full alternative, and that is what shipped.
- Moving executor probe-strategy internals (relay gating,
  _probe_inconclusive) into the policy: they decide how
  evidence is GATHERED, not what it MEANS. verify.py's
  transition table was likewise left alone — it is
  already a separate table-driven module, and the Phase
  153 audit names engine transitions + consent re-checks
  + channel derivation.
- Fixing the six preserved ambiguities (below): an
  extraction that silently "improves" semantics is a
  behavior change in disguise. They are preserved,
  documented in the policy docstrings, and pinned by
  unit tests so any future change is a deliberate,
  visible decision: (1) submit `ok` is judged before
  HTTP status — an ok+403 counts as submitted; (2)
  executor host-guard refusals (ok=False, status=None)
  fail the case as submit_failed, not a block; (3)
  probe-error beats CAPTCHA in branch order; (4)
  missing_field scans only mapped form fields —
  unmapped_fields play no part; (5) the email channel
  keys only on a letter attempt existing, so any
  re-queued email case with a letter on file is treated
  as the user's "I sent it"; (6) unknown-broker is
  decided before the consent re-check.
- An admin-UI button for replay (JSON API only, the
  standing posture of the P2-E metrics blocks); a replay
  attempt row (the audit row is the record; attempts stay
  purely engine actions so their Phase 31 workflow-version
  grouping stays clean); stamping POLICY_VERSION per
  attempt (would have needed a migration and changed
  attempt shapes the harness asserts on).

## SECURITY CONTROLS
Replay is the batch's one new write surface and it is
defended in depth: admin gate with the invisible 404,
the accounts CSRF gate in front of it, per-lane consent
re-checks against the owner's CURRENT consent (a revoked
consent can never be resurrected by an operator action),
typed refusals that leak nothing about other users'
rows, and an audit row for every success. The policy
extraction changes no gate: consent is still re-checked
inside process_case on every run, now as a policy
decision the engine applies.

## PRIVACY CONTROLS
The replay response and audit rows carry no owner data
(kind, id, status, counts, reasons only). The state
mapping publishes vocabulary, not data. Policy unit
tests run on synthetic decision inputs.

## KNOWN LIMITATIONS
POLICY_VERSION is a code constant; nothing historical
records which version decided a past case (attempts
record the WORKFLOW version per Phase 31 — a different
axis, deliberately not conflated). Replay is API-only
(no admin-UI button). The email-channel letter rule
(preserved ambiguity 5) is generous by design; if it
ever mis-fires, the fix is a policy change with a
version bump — now a one-module edit with a test table,
which is the point of the extraction.

## RISKS
The extraction's safety rests on the regression net
(remediation + fake-broker suites, both unmodified and
green) plus the new decision-table tests; any engine
behavior NOT covered by those suites could in principle
have shifted — the staging/production E2E smokes
(full scan, notifications, deletion) passed, and the
removal paths will exercise the policy live as real
cases drain. Replay's job-counter reset is the one
judgment call with blast radius: it is bounded by the
consent re-check, the audit row, and the 3-attempt
budget re-applying immediately after.
